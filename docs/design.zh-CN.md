# LLM 伪造用户话语的双层防护方案

## 1. 问题

在长对话、工具调用或 agent 循环中，模型可能在 assistant 输出末尾继续生成一段并不存在的用户话语：

```text
assistant: 好的，我知道了。

user
[2026-06-11 00:28:24] 哈哈哈
```

更危险的是，这段伪造内容进入 transcript 后，模型下一轮可能把它当成真实历史，继续引用、解释，甚至据此行动。

另一种更隐蔽的变体发生在 reasoning/thinking 中：

```text
她刚才问“你在做什么”，所以我应该……
```

但用户实际上从未说过这句话。

## 2. 总体设计

采用两层防线：

```text
assistant 输出
    │
    ├─ 第一层：输出截断
    │   宿主在展示、保存输出前调用过滤器
    │   识别结构异常并从异常位置截断
    │
    └─ 第二层：下一轮事实纠偏
        用户再次发言时运行 UserPromptSubmit hook
        检查上一轮 assistant 的错误归因
        对照此前真实用户消息，查无时注入纠偏上下文
```

第一层保护当前界面和 transcript，第二层防止模型在后续对话中继续相信自己的幻觉。

这两个接入点不同：Claude Code 的 `UserPromptSubmit` hook 只能实现第二层。第一层必须由能够在渲染或持久化前取得 assistant 输出的宿主显式调用。本仓库提供过滤 API 和 CLI，但不会宣称仅安装 hook 就能拦截当轮展示。

## 3. 第一层：结构性截断

扫描 assistant 可见文本末尾的有限窗口，跳过 Markdown 围栏代码块，仅在行首或整行精确匹配以下特征时截断：

- 单独一行的 `user`、`user:`、`assistant`、`assistant:`、`human:`、`h:`、`a:`
- 带角色前缀的秒级对话时间戳，包括 `user[...]`、`univers[...]`、`universe[...]`
- 角色行后紧随的秒级时间戳
- 行首出现 `mid-stream interruption` 一类内部协议残片

默认窗口为末尾 40 行且不超过 4,000 字符。没有角色边界的裸时间戳按普通日志处理，避免把正常服务日志误截断。

Python 接入示例：

```python
from fake_user_turn_guardrail import split_fake_user_tail

safe_text, finding = split_fake_user_tail(model_output)
if finding:
    write_private_rotating_audit_log(finding.tail)
render_and_persist(safe_text)
```

本库不会自动保存截掉的正文。需要审计时，由宿主把 `finding.tail` 写入权限受限、定期轮转的本地日志；不要展示给用户，也不要把它重新注入模型上下文。

## 4. 第二层：语义错误归因检测

在下一次真实用户消息进入时，读取上一轮 assistant 的正文；平台允许时也读取 reasoning/thinking。一次工具调用型回复可能被 JSONL 拆成多个 assistant 事件，因此实现会把同一真实用户提示之后、下一次真实用户提示之前的 assistant 事件聚合为一个逻辑轮次。

只寻找带引号的近邻归因，例如：

```text
用户刚才说“……”
她刚刚问“……”
上一条用户发了“……”
```

把引号内逐字内容与该逻辑轮次之前的真实用户消息比对。查无时注入纠偏上下文，不修改 transcript。

为了避免把不可信模型输出提升到高优先级上下文，纠偏内容不复制可疑引文，只包含：

- 异常类型
- 异常数量
- 引号归因在该 assistant 正文中的序号
- assistant 正文行号

序号和行号可以在同一回复含有多条真假引用时准确定位异常，同时避免原文构成新的提示注入载体。

## 5. “真实用户消息”过滤

不能简单地把所有 `role=user` 都当成真人输入，因为许多 agent 系统会用 user 事件承载：

- tool result
- 命令输出
- system reminder
- heartbeat 或定时任务
- XML/标签式上下文注入
- memory retrieval 结果

这些事件必须排除，否则注入内容中碰巧出现同一句话，会错误地替模型幻觉“作证”。

只查询目标 assistant 逻辑轮次之前的用户消息。用户随后发来的“我没有说过 X”不属于证据，否则这条纠错消息本身包含 X，会反过来把幻觉洗成“确实出现过”。

## 6. Transcript 尾窗完整性

hook 默认只读取 transcript 最后 300,000 字节，避免每次提示都扫描无限增长的文件。

固定尾窗可能被超大的 tool result 截断。如果窗口中找不到目标 assistant 轮次之前的真实用户提示，就无法证明历史证据完整。此时实现采用保守策略：

- 继续运行结构性边界检测
- 跳过语义错误归因结论
- 不把“没有读到”误写成“用户没有说过”

可以通过 `FAKE_USER_GUARD_TAIL_BYTES` 增大读取窗口。只要窗口内包含目标轮次的真实用户提示，语义检测仍正常运行。

## 7. 精度策略

- 只检查带引号的逐字归因
- 只抓“刚才、刚刚、上一条、主动、直接”等近邻描述
- 不判断无引号释义
- 不检查远期记忆归因
- 排除“如果用户刚才说……”一类假设句
- 只归一化空白，不做大小写折叠或模糊语义匹配
- 围栏代码中的结构示例不触发截断
- 裸时间戳不单独作为伪造轮次证据

目标是低误报，不是覆盖所有幻觉。

## 8. 验收用例

仓库测试至少覆盖：

- 输出末尾出现裸 `user`、`user:`：应截断
- 输出末尾出现 `univers[...]`：应截断
- 裸日志时间戳：不应截断
- fenced code 中出现角色示例：不应截断
- 正常正文讨论相关关键词：不应截断
- “她刚才问‘X’”，历史里没有 X：应指认
- 历史用户确实说过 X：应放行
- X 只存在于 tool result 或系统注入：仍应指认
- “如果她刚才问‘X’”：应放行
- 用户事后说“我没说过 X”：不能洗白此前幻觉
- reasoning 中出现错误归因：平台可读取时应命中
- 同一工具调用轮次拆成多个 assistant 事件：应合并检测
- 大 tool result 截断真实证据窗口：不得误报
- 纠偏上下文应提供序号和行号，但不得复制可疑原文

## 9. 方案边界

- 第一层只能拦截带结构特征的伪造轮次
- 第一层必须接在宿主的输出展示和持久化之前
- 第二层主要防止下一轮继续相信幻觉
- 当轮已经基于 reasoning 幻觉生成的第一条回复未必能及时阻止
- 无引号释义、模糊改写和远期记忆归因默认不检测
- 平台不提供 reasoning 时只能检查可见正文
- 证据窗口不完整时宁可漏报，也不把缺失历史当作反证
- 审计日志由宿主按自身隐私和留存策略实现
- 这不是通用事实核验器

它解决的是一个更具体的问题：避免模型伪造用户话语，并在后续对话中把这段伪造内容不断自我强化。
